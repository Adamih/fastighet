# Fastighet

See README.md for stack, scripts and layout. UI copy is Swedish; code and comments are English.

## Rules

- **Tenant isolation.** Every domain table has `organizationId`. Read and write domain tables only through `orgQuery` (`src/server/scoped.ts`) and always filter on the id it passes in (the company in focus, see Managed companies). D1/SQLite has no row-level security, so queries can't be checked by the database.
  - The database does refuse references across companies. Each domain table has a unique `(organization_id, id)` key (`companyKey`), and references between domain tables are composite foreign keys on it (`sameCompany` in `src/db/schema.ts`), never a plain `.references()`. A new domain table needs both. Only `organization` and `user` are referenced by a single column.
  - Don't use `onDelete: 'set null'` on a `sameCompany` key: it would null `organization_id` too.
  - The admin dashboard (see Admin) is the one place that reads across companies, on purpose, with `query`; `admin_event` is its own log and has no `organizationId`.
  - The management tables (see Managed companies) belong to two companies and name both. The only other tables without `organizationId` are `kpi` and `price_base_amount` (prisbasbelopp), reference data shared by every company. Domain code only reads them (`query`, not `orgQuery`). Their values come from SCB and the government only, through a migration (or `syncKpi` for KPI), never from a form, so no company can change what another one's indexation or fees use.
- **Server code goes through Effect.** Server functions are thin: validate input with an Effect Schema (`Schema.toStandardSchemaV1`) and call `runApp(program)`. Business logic lives in `features/*/program.ts` as Effect programs that use `Database`, `CurrentUser` and `CurrentOrganization`.
- **Active company.** `runApp` checks on every request that the user still belongs to the session's active company, their **home company**. If not (for example after being removed), it switches the session to the user's oldest remaining company, or fails with `NoActiveOrganization` when there is none. Route guards use `getSessionFn().hasOrganization`, which reads the member table, never the session's `activeOrganizationId`.
- **Managed companies.** A company can let another company manage its data (`management_grant`), e.g. a property manager handling BRFs. The manager's staff never become members of it, and nothing switches the session's active company.
  - **The company in focus** is in the URL (`?company=<id>`, kept on every link by the `_app` route's `retainSearchParams`) and reaches server functions as a header from the middleware in `src/start.ts`; during SSR `runApp` reads the page URL (`src/lib/focus.ts`). Without it, requests are about the home company. `runApp` resolves it on every request (`resolveFocus` in `src/server/focus.ts`) and provides it as `CurrentOrganization`, so `orgQuery` and every domain program work unchanged; `HomeOrganization` is always the home company. A company outside the user's scope fails with `CompanyNotInScope`, which redirects home.
  - **Scope:** the home company plus every company with an active grant to it, if the user is assigned there (`management_assignment`) or is an owner or admin at home. Grants don't chain: only grants to the home company count, and management programs refuse to run in a managed company (`requireOwnCompany`).
  - **Permissions there:** the role that applies (the assignment's, else the home role) AND the grant (`managedAllows` in `src/lib/managed-access.ts`, pure and unit-tested). `CurrentOrganization.grant` is null at home and the grant in a managed company; `hasPermission` and `useCan` branch on it. A grant holds raw permissions on domain resources only (`grantableResources`); the team, invitations, `client` and `grant` are never grantable. `viewer` is a read-only role for assignments only, not a Better Auth role.
  - **Setup** (`features/management`): the manager's owner or admin creates a request ("Kundbolag", `client:manage`) with a code shown once and stored as a hash (`codes.ts`), optionally emailed (`managementRequest` template). The managed company's owner (`grant:manage`) enters it under "Förvaltare", sees who asks, chooses the permissions, confirms a processor agreement and approves; changes and revocation apply on the next request. Grants are never deleted (revoking sets `revokedAt`); assignments are keyed by the two companies, so they come back with a new grant. Failed codes are rate limited per user.
  - These tables belong to two companies, so they reference `organization` directly and are read with `query` filtered on the current company's column, never `orgQuery`.
  - Query keys don't name the company; the router clears the query cache when the company in focus changes (`src/router.tsx`). The team, "Alla bolag", "Kundbolag" and "Förvaltare" pages redirect to the home company.
  - Either side can end a grant: the managed company's owner revokes it ("Förvaltare"), or the manager ends it ("Kundbolag", `endClient`, which also writes the event to the client's audit log).
  - **"Alla bolag"** (`features/portfolio`) is read only: it runs each company's own programs (`listInvoices`, `listPayments`, `listUnits`) with that company provided as `CurrentOrganization`, so the same permissions apply, and lists the results side by side. Every row opens its company; writes always happen inside one company.
- **Audit log.** Every write server function passes its action to `runApp` (`runApp(program, audit('invoice.void', data.invoiceId))`; creates omit the id and the result's `id` is used). After the program succeeds, `runApp` records it in `audit_event` with the user, their home company and the company it changed (`src/server/audit.ts`); a failure to record is logged, not thrown. The log stores action keys, never text: labels are messages in `features/audit/actions.ts`, so they follow the UI language. A new write function needs an action there. Team and subscription changes don't go through `runApp`: Better Auth's organization and Stripe hooks (`src/lib/auth-config.ts`) record invitations, joins, role changes, removals and subscription changes through `recordCompanyEvent` (`src/lib/auth.ts`), taking the acting user from Better Auth's request context when the hook doesn't name it. What an id alone doesn't say goes in `details` as plain values (names, role keys, emails). An admin acting as the user is recorded with it (see Admin). The log has no page yet; `managerActivity` (what other companies' staff changed) is the read model for one.
- **Subscriptions and tiers** (`features/billing`). Each company type (`landlord`, `brf`, `manager`) has three tiers: free, a self-serve middle one, and a top one (Förening Pro is self-serve; Fastighetsbolag and Förvaltningsbyrå are sold by sales). Free covers the records a company must keep and its billing cycle; paid tiers add new kinds of work. Never take a feature out of a tier customers have.
  - `tiers.ts` (client-safe, unit-tested) is the only definition: the tiers, the comparison rows and the backstops. A tier allows a feature when its row's cell isn't "no" (`tierAllows`), so changing a cell changes the checks. Rows without a feature describe what isn't built yet.
  - A company's tier (`resolveTier`): one we set (`organization_settings.planOverride`: sales deals invoiced outside Stripe, companies from before subscriptions), else its paying Stripe subscription (active, trialing or past due), else its type's free tier.
  - Programs start with `yield* requireFeature(...)` next to `requirePermission`. Domain features follow the company in focus (a managed company's own tier); a manager's own (`homeFeatures`: clients, Alla bolag) the home company. The UI mirrors it with `usePlan` and shows `PlanHint` where a feature isn't included. Gate new paid work only: existing records stay viewable and correctable after a downgrade (see `requireLeasePlan`).
  - Payment is Better Auth's Stripe plugin (`auth-config.ts`); its `subscription` table is the source of truth, with the company id as `referenceId`. Each paid tier is a plan with the tier id as name and as the Stripe price's lookup key (`stripePlans`). Only the company's own owners and admins buy (`authorizeReference`), from "Abonnemang" (`/plan`).
  - Prices count apartments, or apartments and premises (`quantity`), set as the subscription quantity; Stripe's tiered prices make the bands. Unit writes call `syncPlanQuantity`, which updates Stripe from the next bill (the `Billing` service; a stub in tests). Per-user tiers use the plugin's `seatPriceId`, which follows the members itself. The free tiers' backstops (5 units, 2 users) are ours: `requireRoomForUnit` and Better Auth's `membershipLimit`.
  - Stripe keys are optional secrets (`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`); without them the app runs and the plan page says payment isn't set up. Subscription changes from Stripe's webhooks go to the audit log (`billing.*`).
- **Admin** (`features/admin`, Better Auth's admin plugin). Fastighet's own staff are users with the role `admin` on `user` (company roles are on `member`). Give the first one with `bun run admin:grant <email>` (`--remote` for production); admins then manage each other in the dashboard.
  - Staff stay in `/admin` under their own account: `runApp` redirects them there before loading any company, even if they have a membership. Login, onboarding and invitation routes do too. The admin header signs out through `/sign-out`; customer access uses the audited impersonation flow below.
  - The dashboard (`/admin`, `src/routes/admin*`) has its own layout, apart from the app. Its server functions run through `runAdmin` (`src/server/admin.ts`), not `runApp`: no company in focus, and anyone who isn't an admin, or is impersonating, gets a 404. It lists users and companies, shows a company's tier, members and grants, sets a tier by agreement (`planOverride`), bans and unbans, gives or takes the admin role, and signs users out everywhere. Nobody bans or changes the role of themself, and admins can't be banned.
  - Admins never create, edit or delete users or set passwords: those plugin endpoints are in `disabledPaths`. Each admin action is recorded in `admin_event` (the "Logg" tab); labels are messages in `features/admin/actions.ts`.
  - **Impersonation** ("Agera som användaren"): Better Auth's `impersonateUser` gives the admin the user's session for an hour (`IMPERSONATION_SECONDS`), never another admin's. Starting it is logged (`session.create.after`). While it lasts the app shows a banner with the way back; `runApp` puts the admin on `CurrentUser.impersonatedBy`, and every audit entry made then names the admin (`audit_event.impersonated_by_*`), team changes too. Buying or changing a subscription is refused while impersonating (`authorizeReference`).
- **Team permissions.** The Team page (`/team`) is Better Auth UI's people view (`OrganizationPeople`: users and invitations) on the session's active company, which is the home company; it redirects staff of a managing company home, and they aren't members, so Better Auth refuses them anyway. Role changes, removals and invitations go through Better Auth's organization endpoints, which enforce permissions and the owner protections; its hooks write the audit log. Leaving organizations is disabled server-side through Better Auth's `disabledPaths`. So is deleting one (also `disableOrganizationDeletion`, and our owner role has no `organization:delete`): every domain table cascades from `organization`, so a deleted company would take its accounting records and audit log with it.
- **Permissions.** `src/lib/permissions.ts` defines Better Auth's access-control statements and roles. Permission evaluation uses Better Auth: `auth.api.hasPermission` on the server and `authClient.organization.checkRolePermission` in the UI. Start domain programs with `yield* requirePermission(...)` (`src/server/authorize.ts`): `read` to view a resource, `manage` to create, edit, delete or act on it. Missing access fails with `Forbidden`. Owners and admins have full access; members manage daily work and can only read settings. Deleting still requires the history checks below.
  - Check every affected resource: booking payments requires `payment:manage` and `invoice:manage`; invoice runs also require `lease:read`. Embedded optional data requires read access to its resource (`hasPermission`); invoice seller details use the internal settings loader.
  - Gate navigation and controls with `useCan()` and disable edit forms without manage access. UI checks mirror server checks; they never replace them. Team listing is open to all members, never to staff managing the company (`requireOwnCompany`). Better Auth enforces member/invitation permissions and owner protections.
- **Agreements.** Runs invoice an `agreement`: a lease (`kind: 'lease'`) or a bostadsrätt (`tenant_ownership`).
  - Billing code (runs, rules, matching, reissue) uses only the agreement, its parties (`agreementParty`) and its units. It never uses `leaseTerms`.
  - **Terms are effective-dated.** What an agreement bills is in `charge`: a base charge (`rent` or `fee`), add-ons (optionally for one unit), and one-off amounts (`interval: 'once'`, billed once by the first avi covering their date). Parties (`agreementParty`) and units (`agreementUnit`) have `fromDate`/`toDate` too. Avi lines record the charge kind and charge.
  - A change from a date ends rows the day before and adds new ones; nothing in force is rewritten. Rent and fees: `changeBaseCharge`, which also adds a one-off line for days already billed. Lease parties and units: `changeLeaseFrom`, planned by `planChange` (`features/agreements/changes.ts`). Editing an agreement only corrects its open terms; a billed charge can't be corrected.
  - Billing reads the terms in force through `billFor` (`features/agreements/billing.ts`), and pages through `currentTerms` (`features/agreements/current.ts`). Both are pure and unit-tested.
  - **Index clauses** (`index_clause`, rules in `features/indexation/rules.ts`, unit-tested) follow Fastighetsägarna's clause. They are allowed only on premises let for a fixed term of at least three years (12 kap. 19 § JB): never on apartments, and lease edits that would break this are refused (`checkClauseAllows`). The base rent charge stays as agreed. The yearly "Indexuppräkning" (`runIndexation`, `once()`, `lease:manage`) ends the `index` charge in force and starts a new yearly one: base rent × share × (KPI − base KPI) / base KPI in whole kronor, never negative with the floor. KPI is three months before the adjustment date, from the 1980=100 series (SCB's rebased continuation from 2026). Each adjustment is recorded in `index_adjustment` (one per lease and date, so a repeat changes nothing); days already billed get a one-off line. A missing KPI month blocks the run. The run can email each invoice recipient the new rent (`rentAdjustment` template) after the adjustment is written; a failed or missing email doesn't undo the adjustment, and `index_adjustment.notifiedAt` records a sent notice.
  - The BRF apartment register (`brf_apartment`, keyed by unit) holds andelstal, insats and upplåtelse; a bostadsrätt only links to its apartment.
  - `agreement.endDate` is the last billed day. The lease program derives it with `effectiveEndDate` and writes it in the same batch as the lease terms. A lease's fixed-term end is `termEndDate`.
  - Avier copy their recipient from `invoiceRecipient` (`features/agreements/parties.ts`): every party's name, and the address and email of the party that receives the invoices.
  - Occupancy and status rules take any agreement through `agreementTerms` (`features/agreements/terms.ts`).
  - Bostadsrätter live in `features/ownerships` and use the lease permissions. Their owners hold whole-percent shares that add up to 100 (`ownershipParties`).
  - A sale is a transfer: the sellers' bostadsrätt ends the day before and stays as history, and the buyers get a new one linked by `ownershipTerms.previousAgreementId`. Deleting an uninvoiced buyer bostadsrätt undoes the sale.
  - **Pledges** (pantsättningar, `features/pledges`, rules in `rules.ts`, unit-tested) record lenders' notices on a bostadsrätt for the apartment register. Priority follows the date the notice arrived (`notifiedOn`); a pledge is in force from then until its `releasedOn`. Pledges are never deleted: a release closes one (a mistake too, with a note), and a bostadsrätt that has had a pledge can't be deleted. A pledge stays on the right it was given on: a transfer never moves it, but lets the board release the sellers' pledges in the same batch. Lease permissions apply, as for bostadsrätter. An extract from the register ("Utdrag", `ownershipExtract`) shows a bostadsrätt as of a day: holders then and pledges in force then, in that day's priority order (`pledgesFor(ids, asOf)`). Producing one is audited although it only reads, so its page fetches it from the component, never a route loader (hover preloading would run it).
  - **Confirmations to the lender** (`features/pledges/confirmation.ts`): the förening confirms a registration and a release in writing. The text is Swedish literals in `confirmation-text.ts`, shared by the printable page and the `pledgeConfirmation` email (reply-to the förening). Registering with the lender's email sends it at once; a failed email doesn't undo the registration. Sending by email, or marking one as posted, records `confirmedAt`/`releaseConfirmedAt` on the pledge.
  - **Fees** (rules in `features/ownerships/fees.ts`, unit-tested): a BRF may charge a pantsättningsavgift (at most 1 %) and an överlåtelseavgift (at most 2.5 %) of the prisbasbelopp for the year of the notice or sale, if its bylaws allow. The shares are opt-in company details, stored as basis points; amounts round down to whole kronor. They are one-off charges (`pledge_fee`, `transfer_fee`, no VAT) written in the same batch as the pledge or sale (`feeCharge`), so the next avi bills them; the buyers pay the överlåtelseavgift, as model bylaws say. The board can skip a fee in the form. A year without a prisbasbelopp refuses the fee: add the new year's amount in a migration each autumn.
  - Checks shared by every kind (units free, parties exist, invoice history) live in `features/agreements/program.ts`.
  - People and companies on agreements are in the `party` table (`agreementParty.partyId`, `invoice.partyId`). The register's UI module (`features/tenants`), its `/tenants` routes and the `tenant` permission keep their names; the UI calls them hyresgäster or medlemmar after the company type.
- **Company type and wording.** `organization_settings.kind` is `landlord`, `brf` or `manager`, chosen during onboarding and changeable under Företagsuppgifter (`/company-details`). It decides the tiers; a manager has no properties of its own, so its navigation leaves them out and it starts on "Kundbolag", and only managers manage clients. The app context carries it as `companyKind`.
  - UI wording that follows it comes from `companyTerms` (`features/settings/terminology.ts`), e.g. Hyresgäster or Medlemmar.
  - Documents are named by agreement kind through `documentTerms` (Hyresavi/Hyra or Avgiftsavi/Avgift), so a BRF's rental flats still get hyresavier.
- **Deleting keeps history.**
  - Delete a record only when nothing depends on it, and check first so the user gets a `Conflict` explaining why. Foreign keys are only the backstop.
  - Units that have ever been on a lease, tenants with leases, and leases with invoices can't be deleted. Terminate the lease instead.
  - Edits never touch issued invoices, which keep their own copy of the details.
- **Phone width.** Every page must work at 390 px. Use `src/components/responsive.tsx`:
  - Pair each data table (`className={desktopTableClass}`, shown from `md` up) with a `MobileList` of the same rows, using `MobileListLink` when the whole row opens something.
  - Use `PageHeader` for the title and its primary action, and `FilterChips` for filters (they scroll sideways on phones).
  - On phones, give action buttons and inputs 44 px height (`h-11 sm:h-9`) and make form submit buttons full width.
  - Keep the existing theme tokens; don't add colors for mobile.
- **Forms.** Each entity has one form component (`features/*/…-form.tsx`), used for both create and edit. Edit pages that live under a detail URL use a trailing underscore (`$leaseId_.edit.tsx`) so they don't render inside the detail page.
  - Build forms with `useAppForm` from `src/components/form.tsx`: fields as `<form.AppField name=…>{(f) => <f.TextField … />}</form.AppField>` (also `SelectField`, `SegmentedField`, `SwitchField`), the button as `<form.AppForm><form.SubmitButton>…</form.SubmitButton></form.AppForm>`. Fields create their own ids. Inside a `FormDrawer` the submit button becomes a sticky footer and the drawer asks before discarding unsaved changes.
  - Forms opened in a drawer get a hook in the same file, built on `useFormDrawer` (`src/components/form-drawer.tsx`), e.g. `useAddTenantDrawer` in `tenant-form.tsx`. The hook owns the mutation and cache refresh. Pages call `x.open` from a button; the hook registers the drawer with the app layout (`FormDrawerProvider`), so nothing else is rendered. The drawer slides in from the right on desktop and from the bottom on phones.
  - A page's "Lägg till …" button uses `<Button size="fab">`: floating on phones, ordinary from `md` up. Such pages leave room at the bottom on phones (`pb-20 md:pb-0`).
- **Errors.** Expected failures are tagged errors from `src/server/errors.ts`. `runApp` maps them: `Unauthenticated` redirects to /login, `NoActiveOrganization` to /onboarding, `NotFound` becomes a 404, `Forbidden` shows a generic "no permission" message, and a `Conflict` message is shown to the user. Anything else is logged and replaced with a generic message.
- **Invoices are accounting records.** Never delete or renumber them:
  - Correct a mistake by voiding an unsent, unpaid invoice that has no credit notes (it keeps its number; `voidProblem` in `correction.ts`), or with a credit note (kreditfaktura).
  - **Money is in the ledger** (kundreskontra: `posting` and `ledgerEntry`, rules in `features/ledger/postings.ts`, unit-tested). Every avi, void, credit note, bank payment, allocation (to an avi or to credit), payment by hand, credit use or transfer and refund is a posting whose entries balance, written in the same batch as what it records. Postings are never updated or deleted; an undo or void is a reversing posting (`reversesPostingId`).
  - What an avi owes, has been paid (by payments or credit), was credited and moved to credit, its paid date and its status are derived from its receivable entries (`invoiceMoney`, `statusFromMoney`), never stored. Read them through `invoiceMoneyFor`/`allInvoiceMoney` (`features/ledger/program.ts`). `invoice.creditedOre` is only a cache of its credit notes, written with them, for the one-avi-per-period index.
  - Credit notes (`credit_note`) are accounting records too: never deleted, numbered without gaps per company in their own series, recipient details copied from the invoice. They credit all or part of an invoice (`features/invoicing/credit.ts`, unit-tested). A fully credited unpaid invoice has status `credited`.
  - **Credit balance (tillgodo).** A party's receivable entries without an avi are their credit balance (`creditBalance`, `creditBalances`). An avi never stays overpaid: what a credit note credits beyond what is still owed moves to credit in the same batch (`credit_transfer`). A new avi (invoice run or corrected avi) uses the recipient's credit when issued (`credit_use`), and shows "Avgår tillgodo" and the lower amount to pay. Voiding an avi gives its credit back.
  - Credit is paid back from the tenant page ("Betala tillbaka", `features/accounts`, needs `invoice:manage` and `payment:manage`), which also shows the party's balance and postings. A refund can be undone; a change that would take back credit already used or paid back (e.g. undoing the payment that created it) is refused.
  - A voided or fully credited avi no longer counts for its period (`inForce` in `features/invoicing/correction.ts`). "Ny avi för perioden" issues one corrected avi, linked by `replacesInvoiceId`. The partial unique index on lease and period enforces this. Invoice runs still skip any period that has an avi, so they never reissue a corrected period.
  - Numbers run without gaps per company, and the OCR is the number plus a Luhn digit.
  - Recipient details are copied onto the invoice when it is issued.
  - Period, rent, VAT and due-date rules live in `src/features/invoicing/rules.ts` and are unit-tested. Change them there.
- **Payment reminders** (`features/reminders`, rules in `rules.ts`, unit-tested) go to overdue avier with something owed, once the company's interval has passed since the due date or the last reminder. A reminder is recorded in `payment_reminder` and never deleted.
  - The fee (påminnelseavgift) is opt-in under Företagsuppgifter, at most 60 kr by law, only if agreed in advance, and charged with an avi's first reminder only. It is posted to the avi's receivable (`reminder` posting), so the avi owes it and the reminder asks for it with the same OCR.
  - Sending goes through `once()`; the email is sent first, then the reminder and its fee posting are written in one batch.
- **Bookkeeping export** (`features/bookkeeping`, SIE rules in `sie.ts`, unit-tested) writes the ledger's postings in a date range as SIE type 4 vouchers (faktureringsmetoden), PC8-encoded with CRLF.
  - One posting is one voucher. Series: F avier, voids and reminder fees; K credit notes; B payments, allocations, payments by hand and refunds. Unmatched money sits on the suspense account.
  - Ledger accounts map to BAS accounts through `accountFor` (`accounts.ts`); a company can change the numbers, and only numbers that differ from BAS are stored. Income goes by charge kind and VAT.
  - Every export is recorded in `bookkeeping_export`, so an overlapping export can be warned about. It needs `bookkeeping` permissions, which members don't have.
- **Payments** come from camt.054 bank files (`src/features/payments/camt054.ts`). Like invoices, they're never deleted:
  - Their status moves between matched, unmatched and ignored (`review` is no longer set).
  - A bank reference is unique per company, which makes re-importing safe.
  - An avi's OCR names the payer and the avi meant. The payment goes to that avi first, then to the party's other open avier oldest first, and the rest to their credit (`allocate`, `matchPayments` in `matching.ts`, unit-tested). An old avi's OCR still works, so a standing transfer lands right. Payments without a known OCR wait for a person, who picks the party ("Koppla"); the same rule splits it.
  - Where a payment went is in its allocation postings (`paymentAllocations`), shown in words by `allocationSummary`. Undoing either side (the payment, or "Ångra betalning" on the avi) reverses all of the payment's allocations, on every avi, and puts it back for handling.
- **Client bundle.** Keep Effect programs, `#/db` and `#/lib/auth` out of client code. Import them only from server function handlers. Client-safe constants (e.g. `unit-kinds.ts`) live in separate modules.
- **Shared rules.** Pure logic that both sides need (e.g. `features/leases/terms.ts`) must not import server modules, so the client can use them for previews.
- **Money** is integer öre, never floats. Parse and format with `src/lib/money.ts`.
- **Dates** are ISO strings (`"2026-10-23"`) in the database, the API and the UI. Use the helpers in `src/lib/dates.ts`. On the server, get today's date from the `today` Effect (`src/server/today.ts`), which uses Stockholm time. Never use `new Date()`, because Workers run in UTC.
- Shared field schemas (`OptionalText`, `PostalCode`, `IsoDate`, …) and `blankToNull` live in `src/lib/schemas.ts`.
- **Email.** Send with `sendEmail({ to, template, props })` from `src/server/mail/mailer.ts`. It renders the react-email template and delivers it through the `Mailer` service, which `runApp` provides. Only the mock provider exists so far (`src/server/mail/provider.ts`). It logs emails, including links, and sends nothing.
  - A new template is a file in `src/emails/` that exports a default component, `Props`, `subject(props)` and `PreviewProps`. Register it in `src/server/mail/templates.ts`.
  - Use inline styles only. Many email clients ignore stylesheets.
  - Better Auth sends verification, password-reset and invitation emails through `deliverEmail` (`src/lib/auth.ts`). It hands the send to `waitUntil` and never awaits it, so response time does not reveal whether an account exists.
  - `src/lib/auth-config.ts` must stay loadable by the Better Auth CLI, so it takes `deliverEmail` as a parameter instead of importing the mailer.
- **Auth UI.** Better Auth UI forms use the Swedish locale and the library's error handling; custom auth actions use `authErrorMessage` (`src/lib/auth-errors.ts`). Public routes call `beforeAuthPage` (`features/auth/public-page.tsx`) to normalize `redirectTo` (including legacy `redirect`) before AuthProvider reads the URL. `authDestination` only allows same-site paths. Signed-in staff go to `/admin`; customers keep their destination or reach onboarding through `/`.
  - **Better Auth UI** (better-auth-ui.com, shadcn registry) provides the account pages ("Mitt konto", `/account/profile` and `/account/security`: name, email, password, signed-in devices) and the user menu in the sidebar. Its components are copied into `src/components/auth` (and `src/lib/auth/auth-plugin.ts`) by `bunx --bun shadcn@latest add @better-auth-ui/<item>`; like `src/components/ui` they stay as the registry ships them (not linted or formatted), so an update is a re-add and a diff. Never let the CLI overwrite our existing `ui` components.
  - `Providers` (`src/components/providers.tsx`, in the root document) configures it as its TanStack Start guide does. `Auth` renders sign-in at `/login`, signup at `/sign-up`, verification at `/verify-email`, password recovery at `/forgot-password`, `/reset-link-sent` and `/reset-password`, and callback/error/redirect views at `/auth-callback`, `/auth-error`, `/auth-redirect`. Paths are in `src/lib/auth/paths.ts`; account pages and `/sign-out` still use their existing routes. New passwords require confirmation. Avatars are off (no image storage). Development login shortcuts live beside the sign-in card (`features/auth/dev-logins.tsx`), and load seed credentials only on click.
  - Three auth registry files have a local change marked `Fastighet:`: `sign-in.tsx`, `forgot-password.tsx`, and `verify-email.tsx` carry `redirectTo` through navigation links and the reset email callback. Re-apply it after updating from the registry, so an invitation round trip survives signup, verification and password recovery. The reset route also preserves the missing/expired-link recovery screen.
  - Its copy is the Swedish locale in `src/lib/auth/sv-se.ts`, in the library's locale format (it ships no Swedish). Merged over English, so a key it adds later shows in English until translated there. Our own pages still use Paraglide messages.
  - Its organization plugin (`src/lib/auth/organization-plugin.tsx`, registered in `Providers`) provides the Team page and the "Bolag" tab under Mitt konto (the user's companies and their invitations). We use none of its organization pages: its paths (`organizationViewPaths`) all lead to /team, and creating companies, logos, teams and multiple roles are off. One local change in their code, marked `Fastighet:`: `organization-member-row.tsx` shows no "Leave" button on your own row, since leaving is disabled (and Better Auth's leave endpoint skips the hooks that write the audit log). Re-apply it after re-adding the item.
  - Changing email (Better Auth `user.changeEmail`) asks the current address first (`confirmEmailChange` email), then confirms the new one, so a stolen session can't move the account.
- **Seed data** (`scripts/db-seed.ts`) writes through the app's Drizzle schema and pure rules, so a schema change that breaks it fails `bun run typecheck`.
  - When you add a feature, give it seed data and keep `bun run db:reset` working.
  - Seeded logins are in `scripts/db-seed-constants.ts`. The BRF board login belongs to a second seeded company, Brf Linden. A third, Exempel Förvaltning AB, manages both through grants, with staff assigned in different roles; the seed prints a waiting request code.
- **Schema changes:** edit `src/db/schema.ts`, run `bun run db:generate`, then `bun run db:migrate:local`. Migrations start from one baseline (`drizzle/0000_baseline.sql`); nothing was deployed before it. D1 can't turn foreign keys off, and dropping a table cascades deletes to rows that reference it, so prefer adding columns and tables; rebuild a table only if nothing references it. Never edit `src/db/auth-schema.ts` by hand; use `bun run auth:generate`.
- Use `.validator()` on `createServerFn` (this Start version has no `inputValidator`).
- Server functions are CSRF-protected (same-origin only). When calling them outside the browser, send `Sec-Fetch-Site: same-origin`.
- Program tests run against an in-memory database with every migration through `harness()` (`src/test/harness.ts`).
- Before finishing: `bun run typecheck && bun run check && bun test`.
